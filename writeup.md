# Four Types of C Packaging in Nix

Three of the four types from pargs.c SOPs, with working examples.

---

## Type 1: Standalone Header

A standalone header is an include-only unit that never produces 
object code.

In nix, standalone headers go straight into `$out/include/`. The 
minimus `package.nix` copies `annexb.h` alongside `lldeck.h`, 
`set_priv.h`, and the other headers with `cp annexb.h ... 
$out/include/`.

Consumers reference them via `-I${minimus}/include` on the 
compiler command line, or with angle-bracket includes like 
`#include <annexb.h>`. No linking is needed - the header defines 
no object code, so there is no `.o` or `.so` to link against.

No function definitions, no global variables - only `#include` 
directives, include guards, and `#define` macros (like the ISO 
646 alternative spellings). This makes it safe to include from 
any translation unit without pulling in unwanted symbols.

The header is purely a preprocessor convenience that resolves at 
compile time.

### example `annexb.h`

`annexb.h` wraps every C99 Annex B standard library header behind 
its own include guard (`ASSERT_H`, `CTYPE_H`, etc.) so downstream 
`.c` files can write `#include <annexb.h>` and pull in the entire 
standard library in one line.

## Type 2: Executable Program - `pargs.c`

A C file with `main()` targets an executable binary.
In nix, the build command is a direct `$CC` invocation:

```
$CC -m64 -O2 -std=gnu99 -I${minimus}/include -include annexb.h \
    -include NuClear.h pargs.c -L${minimus}/lib -lNuClear -o pargs
```

The `-I` flag points at minimus headers, `-L` and `-lNuClear` 
link the shared library, and `-include` force-includes headers 
before the source so types are available without explicit 
`#include` lines. After compilation, 
`install -Dm755 pargs $out/bin/pargs` places it in the nix store 

output, and 
`patchelf --set-rpath "${minimus}/lib"`

hardcodes the library path so the binary finds `libNuClear.so` at 
runtime without requiring `LD_LIBRARY_PATH`.

`pargs.c` includes `annexb.h` for standard library access and 
`pargs.h` (generated by makeheaders) for its own prototypes, then 
defines `main()`, the `pargs()` function, and a static `test()` 
helper. The test function exercises `zalloc_unsafe()` from 
NuClear to verify memory allocation works.

The resulting binary is self-contained - it links against 
`libNuClear.so` at runtime for the allocator but carries all its 
own logic.

## Type 3: Shared Library - `NuClear.c`

A `.c` file compiled with `-shared -fPIC` targets a shared object (`.so`).

The makeheaders step generates `NuClear.h` with function 
prototypes and exported macros, while the actual function bodies 
live only in the `.so`. This separation means consumers compile 
against the header but link against the library.

The nix build and install split this into two phases. Build 
compiles the shared object:

### example `NuClear.c`

```
$CC -shared -fPIC -include annexb.h -I. NuClear.c -o libNuClear.so
```

Install copies the header to `$out/include/NuClear.h` and the 
library to `$out/lib/libNuClear.so`. Consumers reference both 
paths: `-I${minimus}/include` for compilation and 
`-L${minimus}/lib -lNuClear` for linking. The `.so` is loaded at 
runtime by the dynamic linker, meaning multiple programs can 
share a single copy of the code in memory. `patchelf --set-rpath` 
on the consumer binary embeds the absolute path to `$out/lib` so 
the library is found without environment variables.

`NuClear.c` defines `zalloc()`, `zalloc_unsafe()`, and the 
`NewClear`/`NuClear` allocation macros, then gets built into 
`libNuClear.so`.

The `-fPIC` flag generates position-independent code required for 
shared libraries - the code must work regardless of where it's 
loaded in memory.

---

## Type 4: Local Library Object File - (not yet implemented)

Type 4 would be a `.c` file compiled to a `.o` object file with 
local includes (`#include "foo.h"`). The target is a single 
translation unit's object code, not a full library. This type is 
used when you want to ship a compiled object that gets linked 
into a larger program but isn't a standalone library. None of the 
current minimus or PIthon sources exercise this pattern yet.
